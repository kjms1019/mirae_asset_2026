→ Gemini로 만든 1차 데모 → 검증용 평가셋** 순서로 정리함. 코드/원본 파일은 GitHub 저장소

## 1. 데이터셋 EDA (전수 분석)

### 1-1. 우리가 받은 데이터가 정확히 뭔지

주최측이 준 `data/3.공시/corpus`는 **70개 상장기업의 DART(전자공시시스템) 공시 원문**임.

- 기업: 70개사 (KOSPI 61 / KOSDAQ 9), 20개 섹터에서 대표기업을 시가총액·산업대표성 기준으로 선정함
- 문서: **4,204건** (원문 XML 파일로는 4,616개), 총 용량 5.15GB
- 기간: 2023년 1월 ~ 2026년 1분기
- 문서 종류 4가지:
  | 종류 | 건수 | 내용 |
  |---|---|---|
  | 정기공시 (periodic) | 1,054건 | 사업보고서·반기보고서·분기보고서 |
  | 주요사항보고서 (major) | 598건 | 유상증자, 합병, 자기주식취득 등 굵직한 의사결정 |
  | 거래소공시 (exchange) | 1,469건 | 공급계약 체결/해지, 신규시설투자 등 |
  | 지분공시 (holding) | 1,083건 | 대량보유상황보고서(5% 이상 지분 보유 신고) |
- 이 중 **1,004건(24%)은 정정공시**임. 원본 공시를 나중에 고친 것.

여기 더해서 `universe.csv`(기업 기본정보 표)와 `manifest.jsonl`(문서 4,204건의 메타데이터. 어느
회사의 어떤 문서가 언제 제출됐는지)이 별도로 제공됨. **이 두 파일이 관제탑 역할을 함.** 원문을 직접
열어보지 않아도 "이 회사에 이런 문서가 있다"는 걸 여기서 먼저 찾을 수 있음.

한 가지 주의: 이 원문 XML은 사람이 보는 PDF 공시가 아니라 **DART가 기업으로부터 제출받는 원본 제출
포맷**임. 우리가 아는 "공시 PDF"는 이 XML을 사람이 읽기 좋게 렌더링한 결과물이고, 우리가 받은 건 그
이전 단계(소스 코드 같은 느낌)라 태그가 그대로 보여서 처음 보면 지저분해 보임. 다만 표 구조(계정과목
-금액 정렬)는 그대로 살아있어서, 잘 파싱하면 오히려 사람이 보는 PDF보다 다루기 좋음.

### 1-2. 핵심 발견 5가지

**① 데이터 자체는 깨끗함 (무결성 100%)**
`universe.csv`에 "이 회사는 정기공시 O건, 주요사항보고서 O건..." 하고 미리 집계해둔 숫자가 있는데,
이걸 `manifest.jsonl`을 직접 세어본 실제 건수와 대조해봄. **70개사 전원 완전히 일치함.** 데이터
자체의 결측·오류 문제는 없다고 봐도 됨.

**② 지분공시(holding)는 "누가 신고했는지"를 헷갈리기 쉬움**
지분공시 1,083건을 열어보면 문서마다 `corp_name`(그 지분의 대상이 되는 발행회사)과 `flr_nm`(실제로
이 서류를 제출한 사람/회사)이라는 두 필드가 있는데, **1,083건 전건에서 이 둘이 서로 다름.**

예: "삼성전자" 문서인데 `flr_nm`은 "삼성물산"인 식임. 즉 이건 "삼성전자가 뭘 했다"는 문서가 아니라
"삼성물산이 삼성전자 지분을 이만큼 갖고 있다"는 문서임. 실제로 확인해보니 국민연금공단, BlackRock
같은 외부 기관뿐 아니라 **우리 70개사 안에서도 서로 지분을 보유한 사례가 11개사·71건** 있었음. 특히
현대차그룹(현대모비스-현대자동차-기아-현대오토에버-현대로템-현대제철)은 6개사가 촘촘하게 얽혀 있고,
심지어 **기아와 현대모비스는 서로가 서로를 보유하는 순환출자** 관계였음.

→ "이 회사 지분을 누가 갖고 있어?"라는 질문에 `corp_name`만 보고 답하면 틀림. `flr_nm`이 진짜
주인공이라는 걸 우리 시스템이 알고 있어야 함.

**③ 4종류 문서 중 거래소공시(exchange)만 완전히 다른 형식**
정기공시·주요사항보고서·지분공시 3종류는 전부 DART 고유의 XML 포맷(태그로 목차가 구획돼있고, 표도
`<TABLE>` 태그로 되어있음)을 씀. 근데 **거래소공시만 확장자는 똑같이 `.xml`인데, 실제 내용물은 그냥
HTML 폼**임(웹페이지에 있는 입력폼 같은 구조). 그래서 이 데이터를 하나의 파서로 다 처리할 수 없고,
**파서를 최소 2종류(DART XML용 / HTML 폼용)로 나눠 만들어야 함.**

**④ 정기공시는 업종이 달라도 목차가 완전히 똑같음**
반도체(삼성전자), 은행(KB금융), 보험(삼성생명), 증권(미래에셋증권) 4곳의 사업보고서 목차를 직접
비교해봤는데, "I. 회사의 개요"부터 "XII. 상세표"까지 **12개 대목차가 100% 동일함.** 업종별로 파서를
따로 만들 필요 없이, **파서 하나로 70개사 정기공시를 전부 커버할 수 있다**는 뜻이라 전처리 작업량을
크게 줄여줌.

(다만 주의할 점: 대목차는 같아도 그 안의 세부 구조(트리 깊이)는 회사마다 미묘하게 다를 수 있다는 것도
데모 만들면서 실제로 겪음. 아래 3번 섹션 참고)

**⑤ 정정공시 비율이 문서 종류마다, 회사마다 크게 다름**
| 문서 종류 | 정정 비율 |
|---|---|
| 거래소공시 | 43% |
| 주요사항보고서 | 28.9% |
| 정기공시 | 15.1% |
| 지분공시 | 3.8% |

회사별로 보면 삼성E&A(63.8%), 삼성바이오로직스(60.7%), 현대건설(55.6%) 같은 건설/EPC 계열 회사들이
압도적으로 높음. 수주 계약 내용이 자주 바뀌기 때문으로 보임.

→ 이게 왜 중요하냐면, "이 회사가 최근에 맺은 계약 조건이 뭐야?" 같은 질문에 **원본 공시만 보고 답하면
틀릴 확률이 꽤 높다**는 뜻임. 원본과 정정본을 시간순으로 연결해서 "최종적으로 뭐가 맞는지"를 추적하는
로직이 없으면 안 됨.

📄 전체 리포트(차트 포함, 브라우저로 바로 열림): `eda/report.html`

## 2. DB / 아키텍처 설계

### 2-1. 우리 전략의 출발점

모든 팀이 **똑같은 데이터셋, 똑같은 LLM(HyperCLOVA X)**을 쓰기 때문에, 모델 자체의 성능 차이보다는
**"데이터를 얼마나 잘 구조화해뒀는가"가 팀 간 실력 차이를 가른다**고 판단함. 그리고 평가에서
closed형(단답형, "얼마인가?")을 먼저 거의 다 맞혀야 open형(서술형, "설명해줘")까지 좋은 점수를 받을
수 있는 구조라고 보고, **closed형 정확도를 구조적으로 보장하는 것**을 최우선 목표로 잡음.

### 2-2. 왜 하나의 DB로는 안 되는가

EDA를 해보니 우리 데이터는 성격이 다른 3가지가 섞여 있었음.

| 데이터 성격 | 예시 | 필요한 방식 |
|---|---|---|
| 완전 정형 (표, 숫자) | 재무제표 요약표, 기업 기본정보 | SQL로 딱 찾으면 끝. 임베딩/검색 불필요 |
| 서사형 텍스트 | 사업 개요, 위험관리 서술 | 의미 기반 검색(RAG) 필요 |
| 얕은 관계 | 정정 이력, 지분/계열사 관계 | 링크 몇 개만 따라가면 됨 (깊은 그래프 탐색까지는 불필요) |

그래서 팀 회의에서 나왔던 "정적 DB냐 Vector DB냐 Graph DB냐"라는 질문에 하나만 고르지 않고,
**성격별로 계층을 나눠서 각자 담당하게 하는 하이브리드 구조**로 결론냄.

### 2-3. 3-layer 구조

**① 구조화 팩트 테이블** (아직 미구현, 다음 단계 최우선)
재무제표 요약표(매출액, 영업이익, 자산총계 등)를 "회사·연도·계정과목 → 숫자값" 형태로 미리 뽑아
SQL/엑셀 같은 표로 저장해두는 것. 이게 되면 "삼성전자 2025년 매출액은?" 같은 질문은 검색·LLM을 아예
거치지 않고 **표 한 줄 조회로 100% 정확하게** 답할 수 있음. 할루시네이션 위험이 원천 차단되는 구간이라
투자 대비 효과가 제일 큼.

**② 벡터 검색 인덱스** (데모로 구현 완료)
서사형 텍스트(사업 개요, 계약 조건 등)를 문단 단위로 잘라서 의미 검색이 가능하게 만든 것. 각 조각마다
"어느 회사, 어느 공시, 몇 년도, 어느 섹션에서 나온 내용인지" 꼬리표를 반드시 붙임. 이게 없으면 "모든
답변에 근거 공시 표시"라는 평가 규정을 지킬 수 없기 때문임.

**③ 관계 엣지 테이블** (아직 미구현)
정정 이력("이 공시가 나중에 어떤 공시로 정정됐나")과 지분·계열 관계("이 회사가 어느 회사 주식을
얼마나 갖고 있나")를 링크 형태로 저장. 앞서 EDA에서 실제로 순환출자(현대차-기아)까지 발견했기 때문에
필요성은 확인됐지만, 회사 수(70개)와 관계 수(1,000여 건) 규모를 보면 **Neo4j 같은 전용 그래프
데이터베이스까지는 필요 없고, 그냥 표 하나 + 파이썬에서 가볍게 순회하는 정도로 충분**하다고 판단함.

### 2-4. 전체 그림

```
DART 원문(XML/HTML)
   ↓ (문서 종류별로 다른 파서)
파싱 → 구조화 팩트 / 벡터 인덱스 / 관계 테이블 (3계층에 각각 저장)
   ↓
질문 라우터: 이 질문이 closed인지 open인지, 어느 계층을 조회해야 하는지 판단
   ↓
필요한 계층만 조회 (여러 개 조합 가능. 예: "A사 B사 비교"는 팩트 테이블 2번 조회 + 계산)
   ↓
LLM이 조회 결과만 근거로 답변 생성 + 출처 표시
```

전체 다이어그램은 `docs/architecture.png`에 있음 (파란색 = 이미 만든 부분, 점선 = 앞으로 만들 부분).

툴을 10개씩 만들지 않고 4~5개(구조화조회/의미검색/정정이력조회/지분조회/비교연산)로 좁힌 이유는,
툴이 너무 많으면 "이 질문엔 어느 툴을 써야 하지?"를 판단하는 라우터 자체가 헷갈려서 오히려 정확도가
떨어질 수 있다는 우려 때문임. 위 3계층에 딱 맞춰 툴을 나누면 라우터의 판단 범위가 좁아짐.

## 3. Gemini 데모 구현

### 3-1. 왜 지금 Gemini로 먼저 만들었나

최종 제출은 HyperCLOVA X를 반드시 써야 하지만, **설계가 실제로 말이 되는지를 빨리 검증**하기 위해
접근이 쉬운 Gemini로 먼저 파이프라인을 돌려봄. (파이프라인 구조 자체는 나중에 HyperCLOVA X로 LLM만
바꿔치기하면 재사용됨.)

### 3-2. 만든 것

- **10개사** (삼성전자·SK하이닉스·현대자동차·기아·NAVER·카카오·LG에너지솔루션·삼성SDI·KB금융·하이브)의
  **가장 최근 사업보고서(FY2025)** 만 우선 인덱싱한 미니 버전임.
- 각 사업보고서에서 "회사의 개요 / 사업의 내용 / 요약재무정보 / 경영진단 및 분석의견" 4개 섹션을 뽑아
  총 551개 조각(청크)으로 나누고 Gemini로 임베딩(의미 벡터화)함.
- Streamlit 웹앱에서 질문을 입력하면: 질문과 가장 비슷한 조각들을 찾아온 뒤 → Gemini에게 "이 조각들
  안에서만 답하고, 근거를 표시해라"고 시켜서 답변을 만듦.
- 평가셋(아래 4번) 문항들을 앱에서 버튼 클릭 한 번으로 바로 물어보고, 정답과 바로 비교할 수 있게
  만들어둠.

### 3-3. 데모 만들면서 발견한 것 (설계를 다시 확인시켜준 사례)

똑같은 질문("삼성전자 vs SK하이닉스 영업이익 비교")을 데모에 던졌더니 **정답은 맞혔지만**, 검색 결과를
보니 정확한 숫자가 있는 "요약재무정보" 표가 아니라 **우연히 "경영진단" 섹션의 서술문에서 답을
찾아왔음.** 즉 순수 의미검색(RAG)만으로는 어쩌다 맞은 것이지, 항상 정답을 보장하지 못한다는 뜻이고,
이게 바로 2-3에서 말한 "구조화 팩트 테이블이 왜 필요한가"를 실제로 증명해준 사례임.

또한 파싱 과정에서, 카카오 같은 일부 대기업은 "회사의 개요" 섹션 하나에 정관 전문·주식발행 이력까지
통째로 들어있어서 섹션 하나가 수십만 자에 달하는 경우, 그리고 하이브 사업보고서에서는 문서 내부의
트리 구조가 다른 회사와 살짝 달라서 파서가 의도보다 큰 범위를 잘못 잡는 경우도 실제로 발견해서 안전
장치를 추가함. → **"대목차는 같아도 내부 구조까지 완전히 같다고 가정하면 안 된다"**는 교훈임.

### 3-4. 로컬 실행 방법 (팀원이 직접 해볼 때)

```bash
pip install -r requirements.txt
cp .env.example .env   # GEMINI_API_KEY 채워넣기
```

## 4. 평가셋 (`eval/eval_set.json`)

### 4-1. 왜 만들었나

대회의 실제 평가문제는 비공개임. 하지만 팀이 만드는 파이프라인이 제대로 작동하는지 확인하려면
"정답을 미리 아는 문제"가 필요해서, 대회 설명자료에 나온 6개 질문 유형(검색및정보추출 / 다중조회및
비교연산 / 복합문서추론 × closed/open)을 본떠서 **우리가 직접 만든 검증용 문제 13개**를 만듦. 전부
실제 원문을 손으로 대조해서 정답을 확인함.

### 4-2. 눈여겨볼 문항들

**"삼성전자와 SK하이닉스 중 2025년 영업이익이 더 큰 곳은?"**
→ 정답은 **SK하이닉스**(47.2조 > 삼성전자 43.6조)임. "삼성전자가 항상 더 크지 않아?"라는 사전지식으로
안일하게 답하면 틀리는 함정 문항임. 모델이 반드시 원문을 확인하고 답해야 한다는 걸 테스트함.

**"LG에너지솔루션이 2024년에 체결한 계약 중 2025년에 해지된 게 있는가?"**
→ 실제로 있었음. Ford Motor Company, Freudenberg Battery Power Systems와 맺은 배터리 공급계약이
2024년에 체결 → 2025년 말에 "공시유보 해제 + 계약해지"로 정정 → 별도 해지공시까지 이어지는 완전한
체인을 원문에서 확인함. 심지어 **정정공시와 해지공시에 적힌 해지 금액이 서로 다름**
(4,082,377백만원 vs 3,921,711백만원). 이런 문서 간 불일치를 스스로 알아채고 "공시마다 금액이 다르다"고
정직하게 답하는지가 근거기반 정확성을 테스트하는 실전 트랩임.

### 4-3. 구성 요약

| 유형 | closed | open |
|---|---|---|
| 검색 및 정보 추출 | 4문항 | 2문항 |
| 다중 조회 및 비교·연산 | 4문항 | 1문항 |
| 복합 문서 추론 | 1문항 | 1문항 |

closed 문항은 "정답"이 정해져 있고, open 문항은 정답 문자열 대신 "채점할 때 확인해야 할 포인트"
목록을 넣어둠 (서술형이라 딱 하나의 정답 문장으로 정할 수 없기 때문).
